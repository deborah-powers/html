** Le plan de test

Plannifier les tests en fonction
De la dangerosité d'une défaillance,
Du nombre de fois où un point risque de planter,
De l'importance de la fonctionnalité
Les tests automatiques permettent de faire vites les tests répétés.
Intégrer le logiciel TODO à finir
Documenter les test permet de prouver l'amélioration du logiciel.
Débogage: Eliminer un bogue. Réactif, proactif
Faire évoluer le plan de test selon l'avancement du projet.

** Les types de test

Unitaire: Chaque fonction marche correctement. Repérer la portion de code où est le bogue
Intégration: Interraction entre plusieurs fonctions
Fonctionnel: Marche d'une fonctionnalité
Acceptation: Le logiciel correspond aux attentes. Souvent fait par le client
Régression: Le nouveau code conserve les anciennes fonctionnalités
Sécurité: Vulnérabilités du logiciel, y compris des données
Performance: Comportement du logiciel dans des conditions définies
Usabilité: Confort d'utilisation du logiciel
Compatibilité: Le logiciel fonctionne dans différents environnements. Android, window, chrome, firefox, etc

** L'assurance qualité

Les test font partie du contrôle de qualité (QC) et concernent les produits.
L'assurance qualité (QA) est un moyen par lequel un vendeur (Bien ou service, surtout en b2b) donne un niveau de qualité à ses produits et prouve sa capacité à la maintenir, y compris à elle-même. Elle concerne les processus.

** La classification des anomalies

-- Les origines des anomalies

L'erreur est causée par les développeurs.
Le défaut vient de défaillances dans les specs ou la documentation. Elles se répercutent souvent dans le code.
La panne (L'échec) apparaît à l'usage quand un logiciel déffectueux est lancé, ou quand la fonctionnalité déffectueuse est sollicitée.

-- Les défaillances dans les tests

Mauvaise interprêtation des résultats du test
Oubli de scénarios de test
Impossibilité de reproduire les conditions d'un cas de test
Défaillance matérielle

-- Les anomalies au quotidien

Anomalie d'interface
Erreur de gestion des exceptions
Erreur de syntaxe
Erreur de complilation
Erreur logique
Défaut de fonctionnalité
Défaut d'intégration, quand un module ne fonctionne pas avec les autres
Défaut de sécurité
Défaut de mémoire, out of bound. Le logiciel veut utiliser une zone mémoire qui ne lui ai pas autorisée

-- Focus sur l'erreur de compilation

Erreur de runtime: La compilation a réussie, l'erreur se déclenche juste après
Erreur de ressources: Le logiciel gère mal les ressources qui le font tourner. Ram, espace disque, etc. Risque de fuite mémoire, etc
Erreur de communication: Dépendance ko, mauvais format de données échangées, protocoles incompatibles

-- Les niveaux d'importance des anomalies

Critique: Fait planter le logiciel
Majeure: Bloque une fonctionnalité
Mineure: Complique l'utilisation du logiciel
Triviale: Défaut esthétique

-- Les niveaux de probabilité de découverte d'une anomalie

Haut: Ano à laquelle les utilisateurs sont régulièrement confrontés
Moyen: Ano apparaissant dans des cas particuliers, ou lors d'opérations peu courantes. Une petite moitié des utilisateurs y sont confrontés
Bas: Rare, concerne peux d'utilisateurs

** Les causes racines des anomalies

La deadline trop sérrées. En général, on saute les phases de test. Les tu sont désactivés et laissé périmer, etc... On se retrouve avec plein de tu qui ne servent à rien et pètent à tord.
Les erreurs humaines
Le niveau des équipiers
La communication dans l'équipe
L'architecture trop complèxe
Les règles de code trop complèxes
Les règles de code trop limitantes
L'utilisation de technologies mal connues
Spec mal écrite ou mal comprise
